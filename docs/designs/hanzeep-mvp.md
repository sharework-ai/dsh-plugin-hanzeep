## Problem Statement

工作中需要 AI 大量生成文档，但生成过程缺少 harness 护栏：质量不可控、结果不可验证。已有两个内部系统各走了半步：cosmic-claude（Python CLI）有 JSON Schema + 审计器（ERROR/WARNING/ADVICE 三级 + 0-100 评分），但审计靠人工触发、无修复循环、规则硬编码在 Python 里；prototype-system（Electron）验证了 JSON + schema + 模板渲染路线，但 schema 校验从未强制执行——是摆设。

## What Makes This Cool

- **场景包生态**：install a pack → generate a document class。每个 pack = schema + generator prompt + checker ruleset + template，社区可贡献。
- **多语言**：pack 原生支持多语言——生成 prompt、渲染模板、关键字类检查规则按语言声明（zh-CN / en-US 起步，迁移 cosmic-claude 的语言包结构），语言由 Config 选择。文档结构与 schema 语言无关，只有表达层（prompt/template/关键字规则）分语言。
- **定位（autoplan 终门 UC1 修正）**：主打差异 = **领域规则包 + 可复验回执 + 闭环胶水**。通用 schema 校验-重试循环已被 instructor/BAML/Guardrails AI 等结构化输出框架占据；未被占据的是"领域规则资产（COSMIC 审计规则族）+ 任何人可重跑复验的回执"组合。闭环仍是核心机制，但不是定位语。
- **闭环护栏（核心机制）**：生成 → schema 校验 → 规则检查 → 失败打回重写 → 直到全绿（无 ERROR，strict 模式可调）。生成器与检查器在文档领域是割裂品类；DITA Skills 最接近但绑定 XML 重标准。
- **验证回执（篡改可见性，tamper-evident）**："全绿"从过程变成产物——每份文档自带机器可读回执（schema 版本、规则集快照、产物内容 hash、语言、迭代次数、逐规则结果、每轮 Issue 计数），任何人重跑 checker 即可复验；`doc_validate` 核对回执中的产物 hash，产物被事后改动即红色回执。防误改不防恶意（无签名）。与 dsh 的"model-visible ⟺ logged"不变量同构。

## Constraints

- 宿主：deepseek-harness（vendored Cordis，TypeScript strict，ESM，.ts 相对导入）
- dsh 规范：capability seam 三角色成套；注册走 ctx.effect()；模型可见输入必须可从 session log 重建；no hardcoded tunables（Config 字段可从 cordis.yml 覆盖）；misconfiguration fails loud；优先用维护中的依赖而非手写轮子
- 测试：Vitest，每文件 100% 行覆盖 gate；模型可见行为变更配 keyless snapshot
- MVP 明确不做：Electron GUI、pack 在线市场、COSMIC 概念进入 hanzeep 核心

## Premises

1. hanzeep 是 dsh 插件（TypeScript/Cordis 契约），不是独立 CLI；cosmic-claude 的审计规则迁移为插件内的规则数据（Spectral ruleset JSON），不调用 Python 子进程。
2. 第一个场景包 = COSMIC 4 阶段文档，迁移 cosmic-claude 已有的 Schema + 审计规则。
3. JSON 是唯一数据源；Markdown 由模板从 JSON 渲染；不过 Schema 校验的文档不算存在。
4. 闭环护栏是核心循环，设最大迭代数防死循环。
5. 核心只有 generator/checker/pack 抽象，无任何 COSMIC 特定概念。
6. pack 支持多语言（用户明确要求）：表达层（prompt/template/关键字规则）按语言声明；语言优先级 tool 参数 > Config 默认，Config 默认缺失时加载期报错、tool 传参不可用时调用期报错。

## Cross-Model Perspective

独立子代理冷读会话摘要后的意见（采纳要点）：

- **验证回执**：全绿应成为可携带、可复验的产物，直接回应 prototype"校验沦为装饰"的教训——校验结果不可见不可携带，护栏就可伪造。
- **golden sample + 变异测试**：每个 pack 附样例文档，故意损坏 N 种方式，断言 checker 全部抓住。这是证明护栏是强制而非装饰的唯一手段，纳入 MVP 验收。
- **Spectral（Stoplight）拿走 50%**：auditor 与 Spectral ruleset（JSON-path 规则、三级严重度、可扩展函数）几乎一对一映射，加 ajv 做 schema，checker 引擎基本不用写。要自建的 50%：pack 抽象、修复回路编排（把规则失败翻译成模型可执行的修复指令——真难点）、dsh 插件接入。
- **保留意见**：子代理建议 MVP 只做 Plan 阶段；本设计采纳其范围（Plan 先行），但核心 API 按链式设计，因为 COSMIC 的价值在 4 阶段链式消费（Req 吃 Plan 的输出）。
- 子代理点名风险："生态是结果不是起点，闭环才是唯一差异化资产"——设计上闭环进核心，生态只体现在 pack 的数据格式（schema/ruleset 是 JSON，天然可分享）。

## Approaches Considered

### Approach A: 规则引擎 + Plan 先行（选定；终门 UC2 修正为引擎 bake-off）
ajv 做 schema 校验；规则检查引擎由 spike bake-off 裁决——@stoplight/spectral-core vs 纯 ajv+微型规则引擎（~100 行）。只实现 COSMIC Plan 阶段，闭环 + 回执 + 变异测试。Effort S-M，Risk Low。探针实证：spectral-core 1.23.1 可跑任意 JSON（无 OpenAPI 绑定），但 CJS-only（与 dsh ESM 契约有互操作摩擦）、自定义函数须经 createRulesetFunction 且接线有摩擦、内置函数不在 core 包。bake-off 裁决标准：可表达规则占比 + 实测接线成本。

### Approach B: 自研 checker 核心 + 4 阶段完整 pack
原生实现 generator/checker/pack 三抽象，COSMIC 4 阶段全量迁移。Effort L，Risk Med。被否：重造 ajv/Spectral 已有轮子违反 dsh 依赖规范；只有一个真实场景时定死 4 阶段 API 易返工。

### Approach C: cosmic-claude 子进程桥
pack 声明外部 checker 命令，包装 Python CLI 子进程。Effort S，Risk Med。被否（终门 T2 修正理由）：审计规则仍硬编码在 Python 里不可配置，违背 pack-as-data 与混合 pack 形态；Python 环境依赖对未来社区用户是分发负担（对自用不是，原否决理由以自用优先视角衡量过重）。

## Recommended Approach

**A**。理由：与"自用优先"选择一致，用最短路径证明闭环这个差异化资产真实可跑；核心 API 按链式设计（每个 pack 声明可消费的上游产物类型），留好 4 阶段扩展位。技术栈：TypeScript + ajv + 规则引擎（bake-off 裁决）+ handlebars + Vitest。

**抽象纪律（终门 T1）**：第二个真实 pack 出现之前不做泛化抽象——MVP 验收只谈 COSMIC 文档产量与质量。

**pack 形态（终门 UC2）：混合 pack**——JSON 声明式规则 + JS 函数清单（跨字段/求和/分级类规则，如 CFP 范围、ID 唯一性）。manifest 带 `version`。golden sample + 变异测试（每规则族 ≥1 种损坏）是每个 pack 的必备契约。

Pack 接口（MVP 形态）：`{ name, version, languages, schema, generators, rulesets, templates, consumes }`。`languages` 列出支持的语言；`generators`（prompt）与 `templates` 按语言提供；`rulesets` 含 JSON 规则与按语言的关键字规则。多语言进 MVP 的成本可控：cosmic-claude 已有 zh-CN/en-US 双语资产可直接迁移。

`consumes` 语义：声明上游产物类型名列表（如 `cosmic-plan`）。生成时提供的上游产物类型必须匹配；失配或缺失在任务启动期报错。根 pack（如 COSMIC Plan）为 `consumes: []`。

## 修复循环设计（核心）

**统一错误格式**：每轮校验产出 `Issue[]`，每条为 `{ ruleId, severity, jsonPath, message, snapshot, suggestion? }`。ajv 的 errors 与 Spectral 的 results 都映射到此格式，下游（修复 prompt、回执、报告）只消费这一种格式。

**修复 prompt 组装**：生成 prompt + 当前产物 JSON + 按 jsonPath 分组的 Issue 清单（每条含 message 与 suggestion）+ 指令："仅修复列出的问题，输出完整 JSON，不要改动未列出的部分"。

**迭代与产物**：每轮产物保留版本（v1..vN）；全绿版本成为正式产物。迭代耗尽（默认上限 5，Config 可调）：fail loud——返回明确错误与红色回执（`isValid: false` + 全部未解决 Issue），不静默采用最后一轮。

**不可解析输出**：LLM 返回非 JSON 或截断时，映射为内部 Issue（`ruleId: internal/invalid-output`，severity ERROR，message 含解析错误摘要），计入迭代并进入下一轮修复 prompt——与校验失败同一条循环路径，不单独重试。

## dsh 集成面

- **注册 tool**：`doc_generate`（入参：pack 名、素材引用列表、语言、可选上游产物引用列表；内部走完整闭环；返回产物路径 + 回执）、`doc_validate`（入参：产物路径、pack 名、语言；对既有 JSON 重跑校验并核对回执，返回回执）。工具调用本身经 session log，满足 model-visible ⟺ logged。
- **素材引用**：字符串列表，每条为工作区内文件路径或内联文本；内联文本以首行 `#!inline` 标记显式区分，不做启发式判断。
- **上游产物引用**：链式 pack 必填；在任务启动期做 `consumes` 类型匹配，失配或缺失即报错。
- **语言优先级**：tool 参数 > Config 默认语言。加载期只校验 Config 默认语言在所有已加载 pack 中可用；tool 传入的语言在调用期校验，不可用即 fail loud。
- **Capability seam**：`doc-pack` Service Definition（pack 注册表与加载语义）、Provider（本地目录 loader）、Consumer（上述两个 tool）。
- **Config 字段**：packs 目录、默认语言、最大迭代数（no hardcoded tunables）。
- **LLM seam**：所有模型调用收敛到单一入口（inject `ctx.llm`），单测在此 mock；每轮 LLM 请求与校验结果记为 session event。

## Success Criteria

2. 变异测试：golden sample 以 ≥5 种方式故意损坏，checker 全部抓住（护栏非摆设的证明）。

5. 多语言：同一 pack 在 zh-CN 与 en-US 下各生成一份通过全绿校验的 Plan 文档；tool 传入不支持的语言时调用期报错，Config 默认语言缺失时加载期报错。
6. 回执复验：`doc_validate` 对未改动产物返回全绿回执；对事后篡改的产物（hash 不符）返回红色回执。
7. 质量门：Vitest 每文件 100% 行覆盖 + keyless snapshot 全绿。
